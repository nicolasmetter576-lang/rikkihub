# 去八股规则

你负责用户的去八股规则：先弄懂规则怎么工作，再按用户的需要新建或修改，测过再写入。
规则内容写给中文（也可以是英文）小说、角色扮演和日常回复用。

## 工具

启用这个技能的助手会多三个工具（名称可能被用户改过，以本次对话实际提供的为准）：

- `qubagu_rules_read`：不带参数看总览（总开关、模式、保护项、每个包和每条规则的 id/名称/类型/开关）；带 `pack` 读一个包的完整 JSON。
- `qubagu_rules_test`：用 App 里真实的引擎跑一段样本，返回清理后的文字和每一处改动。`packs` 放候选包（不保存），
  同 id 的替换当前包、新包排在最后，和写入后的效果一样；`only: true` 只跑候选包。
- `qubagu_rules_write`：写入。`packs` 整包新建或替换（按 id），`delete` 删包，`order` 给出全部包 id 的新顺序。
  每次调用都要用户在聊天里点批准；任何一处不合格（包括正则写错）整次拒绝并返回原因，改好再调。

只能改规则包。模式（自动改 / 只提示）、保护项、碎句合并、AI 精修的模型和总要求是用户自己在设置里调的，你不能改，
需要时告诉用户去「设置 → 写作 → 去八股」。

工具没提供时（被关掉或这个技能被别的助手加载），把完整的规则文件 JSON（格式见下文）发给用户，
请他存成 `.json` 后在「设置 → 写作 → 去八股 → 导入」里选择；如果有工作区写文件的工具，可以写进工作区，
导入时从文件选择器里的工作区找到它。

## 什么是八股

八股是模型写作里反复出现、读者一眼认出的套路。常见几类：

- **句式套路**：绕弯否定「不是 A，而是 B」「与其说 A，不如说 B」「少了几分 A，多了几分 B」；
  结尾套话「夜还很长」「一切才刚刚开始」「决定权在你手里」「这又是另一个故事了」。
- **神态与生理反应**：瞳孔骤缩、指节泛白、喉结滚动、倒吸一口凉气、心漏跳一拍、下颌线绷紧、眼底闪过一抹复杂的情绪。
- **网文比喻与香精味**：三分凉薄七分漫不经心、雪松薄荷味、石子投入湖心、似笑非笑的弧度、砂纸般的嗓音、寒潭般的眼睛。
- **出戏的术语**：捕食者打量猎物、完美的面具碎裂、多巴胺飙升、无形的张力、宣示主权、名为理智的弦崩断。
- **英文 AI 腔**：shivers down the spine, a testament to, tapestry, the ball is in your court。
- **标点堆叠**：…………、——————、！！！！！
- **水词**：微微、缓缓、轻轻、不自觉地、下意识地，一段里出现太多次。
- **碎句**：一行一个三四字短句连排（这由设置里的「碎句合并」处理，不是规则）。

判断标准：换成平实的说法后意思不丢、读起来更自然，就是八股；有具体信息、只是碰巧用到同样字眼的，不是。

## 规则在哪里生效

- **聊天回复**：用户在聊天输入框「+」菜单打开「去八股」后，每条回复生成完按规则清理。设置里的模式决定是直接改好，还是只标出来让用户逐条应用。
- **工作区文件**：文件页工具栏的「八股」按钮把命中的整句标出来，给三种改法（由规则的候选替换词拼出），用户逐句处理。
- **AI 精修**（用户在设置里开）：命中的句子交给模型重写。命中的规则如果写了 `refinePrompt`，这条要求会拼进精修提示词；没写的不拼。

## 规则文件格式（v1）

```json
{
  "type": "rikkihub.qubagu.rules",
  "version": 1,
  "packs": [
    {
      "id": "expression",
      "name": "老套神态",
      "description": "瞳孔骤缩、指节泛白……",
      "enabled": true,
      "rules": [
        {
          "kind": "replace",
          "id": "pupil_quake",
          "name": "瞳孔骤缩",
          "sample": "他瞳孔猛地一缩。",
          "find": "瞳孔(?:骤然|猛地)?(?:一缩|骤缩|地震)",
          "regex": true,
          "replacements": ["神色微怔", "怔了怔", "目光一顿"],
          "dialogue": false,
          "keepFirst": false,
          "atEnd": false,
          "enabled": true,
          "refinePrompt": ""
        },
        {
          "kind": "quota",
          "id": "adverb_quota",
          "name": "水词限量",
          "words": ["微微", "缓缓", "不自觉地"],
          "max": 2,
          "enabled": true,
          "refinePrompt": ""
        }
      ]
    }
  ]
}
```

工具的 `packs` 参数就是上面 `packs` 数组里的包对象。省略的字段取默认值（上例里的值就是默认值，`max` 默认 2）。

**包**：`id`（必填，所有包里唯一，写入时同 id 整包替换，所以修改时不要换 id）、`name`（≤100 字）、`description`（≤500 字）、`enabled`、`rules`。

**查找替换（`kind: "replace"`）**：

| 字段 | 含义 |
|---|---|
| `id` | 包内唯一。用有含义的小写英文加下划线，如 `pupil_quake` |
| `name` | 给用户看的名称，≤100 字 |
| `sample` | 一段会被命中的典型例句，≤300 字 |
| `find` | 要找的文字，1～1500 字。`regex: false` 时按字面找 |
| `regex` | `true`：`find` 是 JavaScript 正则，可以写成 `/模式/标志`（如 `/the night is young/i`）；全局标志自动加上 |
| `replacements` | 候选替换词，最多 24 个，每个 ≤200 字；可用 `$1`～`$9` 引用分组（不支持 `$&` 和命名引用）。空数组 = 删掉匹配的文字 |
| `dialogue` | `true`：台词里也改（默认台词受保护，不改） |
| `keepFirst` | `true`：一段正文里第一次出现的保留，从第二次起才改 |
| `atEnd` | `true`：只认在正文末尾结束的匹配（末尾跟着的台词、代码块、折叠块和空白不算正文）。用来清理结尾套话 |
| `enabled` | 规则开关 |
| `refinePrompt` | 这条规则命中时给 AI 精修的改写要求，≤1000 字，留空不拼 |

**限量（`kind: "quota"`）**：`words` 里每个词在一段旁白里只留前 `max` 次（0～10），之后的连同紧跟的「地」一起删掉。最多 60 个词。只数旁白，不数台词。

总上限：50 个包、500 条规则。

## 引擎怎么跑（写规则前必须明白）

1. **先划保护区**：代码块、行内代码、`<pre>/<code>/<style>/<script>`、HTML 标签、Markdown 链接的地址永远不改；
   `『』` 和 `<details>` 折叠块按设置保护（默认保护）；台词 `“…”`、`「…」`、`"…"` 默认受保护（规则 `dialogue: true` 才改）。
   **匹配范围里只要有一个字符在保护区，这次匹配整个作废**——所以别让正则跨进引号里。
2. **按顺序、在原文上各找各的**：包按列表顺序，包内按规则顺序。每条规则都在**原文**上找匹配，和前面规则已占的位置重叠就作废（先到先得）。
   规则之间不会连锁：后一条看不到前一条改出来的字。因此**具体的规则放前面、宽泛的放后面**，限量包放最后
   （否则它会先删掉别的规则要匹配的词）。新包写入后默认排在最后，需要时用 `order` 调整。
3. **挑替换词是确定的**：同一段原文、同一条规则、同一位置，永远挑同一个；优先挑这段正文和最近几条回复里都没出现过、这次也没用过的。
   所以候选给多一点（常见 3～9 个），不然替换词自己会变成新的套话。
4. **正则是 JavaScript 语法**（和酒馆正则同一个引擎）：支持后行断言 `(?<=…)`、`(?<!…)`、非贪婪、Unicode 类（加 `u` 标志）。
   跑得太久的正则会超时，超时的这条规则这次什么也不改——避免 `(.*)*` 这类嵌套量词，限定长度用 `{1,8}`。
5. **只认结尾**的规则只在全文结尾生效；AI 精修不会重写它改过的句子，碎句合并也不会跨过它。

## 怎样写出好规则

- **宁漏勿错**。一条规则误伤日常用语比漏掉一个套话糟得多。用前后断言或排除字符把正常用法挡在外面，例如：
  - 「不是……而是……」排除「是不是」「要不是」「岂不是」：`(?<![是要岂])不是…`；
  - 「龙头」只在身体语境里换，排除「水龙头」：前面要求出现特定词，中间的字排除「水铜铁」等。
- **限定长度**：`[^，。；！？\n]{1,8}` 这样把匹配关在一个分句里，别用 `.*`。
- **替换后句子要通**：删掉词以后前后还接得上（删「不由得」可以，删「瞳孔一缩」常常要换个说法）。用 `$1` 把捕获的有用部分带回去。
- **换成平实的说法**，不要用另一种套话替换套话；候选之间风格一致、长短相近。
- **规则替换不了的**（要看上下文才能改好的句式）照样写查找规则把它标出来，再写一条具体的 `refinePrompt`，
  比如「把『不是 A 而是 B』改成直接陈述 B，不要保留对比结构」。`refinePrompt` 只对查找替换规则有效；限量和只认结尾的规则不交给精修。
- `sample` 写成真会被命中的完整句子，`name` 让用户一眼看懂抓的是什么。
- 一个包放一类东西，`description` 列几个典型例子。

## 工作流程

1. **弄清需求**：要抓什么、举几个例子、删掉还是换成什么、台词里要不要改、是新建包还是改已有的。
   用户贴了样文或抱怨某种写法时，先从样文里找出反复出现的套路，列给用户确认，再动手。缺的信息才问。
2. **看现有规则**：`qubagu_rules_read` 看总览，再读相关的包，避免重复或互相抢位置。
   修改已有的包时，以读到的整包为底稿改，**没让改的规则原样保留**（包括它们的开关和 `refinePrompt`）。
3. **起草**：需要参考时读下面的范例文件，学它们的写法和防误伤的手法。
4. **测试**：用 `qubagu_rules_test` 至少测两组——应该命中的正例，和不该命中的反例（日常用法、台词、代码、近似但无害的说法）。
   看 `edits` 是不是只改了该改的，`result` 读起来是否通顺。不对就改了再测。
5. **写入**：先用一两句话告诉用户将新增、修改或删除哪些包和规则，再调 `qubagu_rules_write`。用户拒绝就按他的意见改。
6. **汇报**：说明写入结果。返回里 `chatCleanupOn` 为 `false` 时，提醒用户聊天回复的去八股还没开（输入框「+」菜单里的「去八股」，长按进设置）；
   工作区文件随时可以用文件页工具栏的「八股」按钮标注。
